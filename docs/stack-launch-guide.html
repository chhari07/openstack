Stage 2 · Week 1

MAKE IT STORE-READY

Code changes that stop Play from rejecting the app and keep AI costs safe. Commit after each one.

1
Two builds: Play and sideloadAdd a build switch (for example STACK_STORE=play). In the Play build, scripts/android-setup.mjs leaves out MANAGE_EXTERNAL_STORAGE and the "scan the whole phone" button. PDFs come in through the folder picker (SAF) and Share to Stack. The sideload APK can keep full scanning.
2
Hide SpotifySpotify caps you at 25 users. Remove it from the Play build, or keep it under Settings → "Advanced: use your own Spotify Client ID". Phone music stays.
3
News: summary + linkFor news cards, show the headline, a short summary and "Open original". Keep full reader mode only for articles the user saved.
4
AI: cheap by default, capped per userSet AI_MODEL=claude-haiku-4-5 for everyday tasks. Keep AI_DAILY_LIMIT low (for example 20 per user per day). The in-memory limit resets when Vercel restarts, so move the counter into Firestore before you have many users.
5
Point the app at the real serverThe APK build uses NEXT_PUBLIC_AI_URL=https://stackforge.in (or the Vercel URL) instead of 10.0.2.2. The emulator cleartext rule should apply to debug builds only.
6
Account deletion inside the appPlay requires apps with sign-in to let users delete their account and data. Add Settings → Account → "Delete account": remove users/<uid> from Firestore, the user's Storage files and the Auth user.
7
Crash and usage numbersAdd something simple to count installs, active days and reviews done (Firebase Analytics or your own Firestore counter). You'll need day-1, day-7 and day-30 numbers.
8
Version numbersIn android/app/build.gradle, set versionCode 2 and versionName "1.0.0", and add 1 to versionCode for every upload.

The Android app needs your server for AI and sign-in checks. Play needs public web pages for privacy and account deletion.

Deploy to VercelImport the repo, framework Next.js, and add these environment variables (Production):

2
Connect the domainVercel → Domains → add stackforge.in and follow the DNS steps. HTTPS is automatic.
3
Firebase for productionFirebase console → Authentication → Settings → Authorized domains: add stackforge.in and your Vercel URL. Then push the security rules:
firebase use openstack-28bf7 firebase deploy --only firestore:rules,storage # Storage only if you're on the Blaze plan
4
Public pagesAdd three simple pages to the site:
/privacy: what's stored on the phone, what's synced (email, notes, highlights, PDFs if uploaded), that AI text goes to Anthropic for processing, and how to delete it.
/delete-account: steps to delete in the app, plus an email option for people who've uninstalled it.
/: a landing page with the logo, one line ("Stack makes you remember what you read"), screenshots and a "Get it on Google Play" button.
5
Smoke testFrom a phone on mobile data (not your Wi-Fi): open the site, sign in with Google, save a note, run one AI summary and check that the note appears on the web. If any of these fail, fix it before Stage 4.

Stage 4 · Week 2

THE RELEASE BUILD

Play takes an Android App Bundle (.aab) signed with your upload key. Google then re-signs it with the app signing key it keeps (Play App Signing).

1
Create your upload key (once)Keep it outside the repo.
keytool -genkeypair -v -keystore ~/keys/stackforge-upload.jks \ -alias stack -keyalg RSA -keysize 2048 -validity 10000 # back up the .jks file and its passwords in 2 places (e.g. a password manager + a USB drive)
2
Tell Gradle about itCreate android/keystore.properties, add it to .gitignore, and read it in android/app/build.gradle:
# android/keystore.properties (never commit) storeFile=/home/aman-kumar-chhari/keys/stackforge-upload.jks storePassword=… keyAlias=stack keyPassword=… // android/app/build.gradle def ks = new Properties(); ks.load(new FileInputStream(rootProject.file("keystore.properties"))) android { signingConfigs { release { storeFile file(ks.storeFile); storePassword ks.storePassword keyAlias ks.keyAlias; keyPassword ks.keyPassword } } buildTypes { release { signingConfig signingConfigs.release } } }
3
Build the bundleCopy build-apk.sh to build-aab.sh and change the last steps:
STACK_TARGET=apk STACK_STORE=play npx next build node scripts/android-setup.mjs && npx cap sync android (cd android && ./gradlew bundleRelease) # → android/app/build/outputs/bundle/release/app-release.aab
4
Fix Google sign-in for the store buildAfter the first upload, go to Play Console → Test and release → App integrity and copy the app signing key SHA-1 and upload key SHA-1. Add both in Firebase → Project settings → your Android app → Add fingerprint. Without this, Google sign-in fails on Play installs even though it works on your debug APK.
5
Test the release build on a real phoneInstall it through the internal testing track (next stage) and repeat the smoke test: sign-in, save, AI, sync, music, notifications, dark mode.

Stage 6 · Weeks 2–5

12 TESTERS × 14 DAYS

New personal developer accounts must run a closed test with at least 12 testers opted in continuously for 14 days before Play lets you publish to everyone. Treat it as your first real user research, not a chore.

1
Internal testing first (day 0)Test and release → Testing → Internal testing → upload the .aab → add yourself and 2–3 friends. It's live in minutes, so use it to catch install and sign-in problems.
2
Start the closed test (day 1)Testing → Closed testing → create a track → add the tester emails (a Google Group is easiest) → upload the same build → send for review. The first review can take a few days.
3
Get testers opted inSend each tester the opt-in link from the track page. Invite 15–20, because anyone who opts out resets their own 14-day count. Check the tester count in the Console every few days.
4
Give them something to doDay 1: "Save 3 articles or PDFs and highlight one line." Day 3: "Do the morning review." Day 7: a 5-question Google Form (What did you use? What confused you? Would you miss it? Would you pay ₹99? What's missing?).
5
Ship 1–2 updates during the testFix the top complaints and upload new builds to the same track (bump versionCode). Google looks at whether you actually tested and improved the app.
6
Apply for production (day 15+)Dashboard → Apply for production. Google asks how you recruited testers, what feedback you got and what you changed, so answer from your notes and form results. A review usually takes about a week.
Where to find testers
College and alumni WhatsApp groups · dev.to / Reddit r/androidapps "looking for testers" posts · Discord servers you're in · friends who read a lot · people who used Pocket. Offer free Stack Plus for a year as thanks.

Stage 7 · Week 6

LAUNCH DAY

Once production access is approved, launch in a controlled way and make noise in the same week.

1
Staged rolloutProduction → create release → rollout 20%. Watch Android vitals (crashes, ANRs) for 2 days → 50% → 100%. You can halt a rollout if something breaks.
2
Make the GitHub repo publicBefore flipping it: run a secret scan again, add a LICENSE (AGPL-3.0 protects the open core from closed clones; MIT is simpler if you want maximum reuse), a CONTRIBUTING.md, and a README that links to the Play Store and stackforge.in.
3
Update the landing pageAdd the Play badge, 3 screenshots, a 30-second screen recording and an email signup for "Stack Plus is coming".
4
Post the launch storyThe same week, post on: LinkedIn (build story + video), dev.to ("I built a local-first reading app with Next.js + Capacitor"), Reddit (r/androidapps, r/IndiaTech, r/productivity; follow each community's self-promotion rules), X, college groups, and Product Hunt on a Tuesday–Thursday.
5
Ask your testers for reviewsYour 12–20 testers can now leave public reviews. Early 4–5★ reviews matter a lot for store ranking.

After launch · Days 1–30

THE FIRST 30 DAYS

Launch is the start of learning. Keep a steady weekly rhythm and only fix what users actually hit.

EVERY DAY · 15 MIN

  • Reply to every Play review and email (even 1★). Thank people and say what you'll fix
  • Glance at crashes/ANRs in Android vitals and the Anthropic usage page

EVERY SUNDAY · 1 HOUR

  • Write down: installs, day-1 / day-7 / day-30 active, reviews done per user, AI cost
  • Pick the top 3 problems from reviews, the form and analytics. Those are next week's work

EVERY WEEK · ONE UPDATE

  • Small, frequent releases (bump versionCode, short "What's new")
  • One public post a week: a feature, a lesson learned or a number you hit

DAY 30 · DECIDE

  • Day-30 retention ≥ 25%: keep going and start Stack Plus (Play Billing) in month 2
  • 10–25%: interview 10 users; change the core loop, not the marketing
  • < 10%: rethink who Stack is for before adding anything new

WHEN THINGS GO WRONG

ProblemWhat to do
Google sign-in fails on Play installsThe Play app signing SHA-1 is missing in Firebase (Stage 4, step 4)
Play rejects the appRead the email carefully, fix only that item, reply through the Policy status page. Don't resubmit unchanged
AI bill jumpsLower AI_DAILY_LIMIT; check for loops; the Anthropic spend cap stops it anyway
A bad release is outHalt the staged rollout, fix, upload a higher versionCode
Lost the upload keyPlay Console → App integrity → request an upload key reset. The app signing key is safe with Google

Good to know

RULES & NOTES

Never
  • Commit .env.local, google-services.json, the .jks or keystore.properties
  • Put ANTHROPIC_API_KEY in a NEXT_PUBLIC_ variable (it would ship inside the app)
  • Upload a debug-signed build to Play
  • Change the app ID com.chhari.stack after publishing: it would become a new app
  • Ask testers for fake reviews or pay for installs
Always
  • Build releases from a clean, committed state and tag them (git tag v1.0.0)
  • Keep a CHANGELOG.md: it becomes the "What's new" text
  • Test every release on a real phone, on mobile data
  • Keep the sideload APK and the Play build on the same version numbers
  • Answer users within a day in the first month
